### 🔴 C1 — كود لا يُصرَّف (compile error)

| | |
|---|---|
| **التقرير §4.2** | `class AppColors { … success, warning, danger, info … }` |
| **نظام التصميم §2.2** | `class AppPalette { … present, late, absent, excused … }` |

مشكلتان:
1. **اسمان لنفس الشيء** — `AppColors` (موجود فعلاً في `lib/core/theme/app_colors.dart`) مقابل `AppPalette` (جديد). لو نُفّذ الاتنين، هيبقى عندك مصدرَي حقيقة للّون.
2. 🔴 **`static const late = Color(0xFFD97706);` — `late` معدِّل محجوز في Dart.** المحلّل بيقراه كـ modifier مش كاسم. الكود ده مش هيُصرَّف.

**✅ الحسم:**
- اسم واحد: **`AppColors`** (نُبقي الملف الموجود، نستبدل محتواه — بدون rename churn عبر ٤٠+ ملف).
- طبقتان منفصلتان بوضوح:

```dart
// lib/core/theme/app_colors.dart
class AppColors {

  static const primary      = Color(0xFF1B5E4A);

  static const primaryLight = Color(0xFFE6F2EE);
  static const accent       = Color(0xFFC9A227);   // ذهبي — الإنجازات فقط

  static const success = Color(0xFF16A34A);
  static const warning = Color(0xFFD97706);

/// تعيين حالات النطاق على الطبقة الدلالية — لا ألوان جديدة.
/// `late` كان اسماً محجوزاً؛ استُبدل بـ `attendanceLate`.
class StatusColors {
```

### 🔴 C2 — ترتيب المراحل خاطئ (أغلى تعارض)

| | |
|---|---|
| **التقرير §السادس** | المرحلة ١ = المجموعات (أسبوع ٣–٦) ← ثم المرحلة ٢ = الثيم والـUI (أسبوع ٧–٩) |
| **نظام التصميم §7** | «الأسبوع ١» = الثيم والألوان والخطوط (يقول إنه يندمج مع المرحلة ٢) |

**التعارض:** الوثيقتان بتقولوا «أسبوع ١» لحاجتين مختلفتين. لكن المشكلة الحقيقية أعمق من التسمية:

> المرحلة ١ بتبني **٨ شاشات جديدة** (قائمة الحلقات، إنشاء، تفاصيل بأربع تبويبات، محرّر الجدول، الحلقة المباشرة). لو اتبنَت على الثيم القديم، المرحلة ٢ هتعيد تنسيقها كلها.

وأسوأ: نظام التصميم §3.3 بيطلب **رفع المتن من 14sp إلى 16sp**. تغيير ده بيكسر تخطيط **كل** كارت وقائمة موجودة. تعمله بعد بناء ٨ شاشات = تصلّح ٨ شاشات زيادة.

**✅ الحسم: أساس التصميم يتقدّم قبل المجموعات.**

```
❌ الترتيب الأصلي:   [بيانات] → [٨ شاشات] → [ثيم] → إعادة تنسيق ٨ شاشات
✅ الترتيب المعدّل:   [بيانات] → [ثيم] → [٨ شاشات على الثيم الجديد]
```

Sprint 1 الجديد (أسبوع ٣) = **رموز التصميم فقط، صفر شاشات جديدة**. تكلفته أسبوع واحد، وبيوفّر ~أسبوعين إعادة عمل.

**ما يبقى مؤجّلاً للـ Sprint 4:** الأصول التي لا تؤثّر على التخطيط — الأيقونة، الـsplash، الرسوم التوضيحية، Hero، العدّادات. دي بتتضاف *فوق* شاشات جاهزة بدون إعادة بنائها.

### 🟠 C3 — تصميم صف الحضور

| | |
|---|---|
| **التقرير §2.5** | «Segmented Button، لا Dropdown ولا Dialog» — `[✓][✗][⏰][📄]` |
| **نظام التصميم §4** | يرفضه (٥٥px < ٤٤ الآمنة) ويقترح السحب |

**✅ الحسم: نظام التصميم يفوز** — قاعدة أهداف اللمس CRITICAL.

**لكن** تنفيذ السحب فيه فخّان لازم يتحطّوا في الخطة:

1. 🔴 **`Dismissible` في RTL معكوس.** `DismissDirection.startToEnd` في واجهة عربية = سحب **لليسار** لا لليمين. لازم تُكتب بالمنطق المنطقي (`startToEnd`/`endToStart`) لا الحسّي (`left`/`right`)، وتُختبر فعلياً في RTL.
2. 🔴 **`Dismissible` بيشيل العنصر افتراضياً.** إحنا عايزين نغيّر حالة لا نحذف صف. لازم `confirmDismiss` يرجّع `false` دايماً بعد ما يسجّل الحالة:

```dart
Dismissible(
  key: ValueKey(student.id),
  confirmDismiss: (dir) async {
    final status = dir == DismissDirection.startToEnd
        ? AttendanceStatus.present    // ← تحقّق من الاتجاه في RTL قبل التثبيت
        : AttendanceStatus.absent;
    await ref.read(attendanceProvider.notifier).set(student.id, status);
    HapticFeedback.selectionClick();
    return false;   // ← يمنع حذف الصف
  },
  child: StudentAttendanceRow(...),
)
```
3. الحالتان النادرتان (متأخر/مستأذن) عبر ضغط الـ Chip → `showModalBottomSheet`.
4. «تحضير الكل» يبقى فوق (من التقرير — لا تعارض).

| الإصدار | Sprint | التغييرات | الخطورة |

### تحذيرات تنفيذية

🔴 **v3 هو الأخطر.** SQLite ما بيدعمش `ALTER COLUMN` — تحويل `studentId` لـ nullable معناه **إعادة إنشاء الجدول** (`m.alterTable(TableMigration(...))` في drift) مع نقل كل الصفوف. لازم:
- نقل `attendanceStatus` لـ `SessionAttendances` **قبل** إعادة إنشاء `Sessions`، لا بعدها.
- اختبار على قاعدة بيانات فيها بيانات حقيقية، مش فاضية.
- كل الـmigration جوّه transaction واحدة.

✏️ **تصحيح على الإصدار الأول من هذه الخطة:** كنت افترضت إن تفعيل `PRAGMA foreign_keys = ON` ممكن **يفشل فتح القاعدة** لو فيه صفوف يتيمة موجودة أصلاً. ده غير دقيق — SQLite لا يتحقق من البيانات الموجودة رجعياً عند تفعيل الـ pragma؛ التفعيل بيؤثر فقط على عمليات DML **لاحقة**. فتح القاعدة آمن ١٠٠٪ بغضّ النظر عن وجود يتامى.
لكن تنظيف الصفوف اليتيمة يفضل مهماً لسببين: (١) صحة البيانات — يتامى بيسرّبوا لعدّادات التجميع (مثال: `DashboardService.getAll()` بيحسبهم ضمن `totalSessionsEver`). (٢) بمجرد التفعيل، أي محاولة **حذف** أب لسه له صفوف يتيمة تابعة له هتُرفض بقيد FK — فالتنظيف دلوقتي بيمنع مفاجأة مستقبلية عند الحذف.

⚠️ **`beforeOpen` بيشتغل كل فتحة** لا مرة واحدة — `PRAGMA foreign_keys` مكانه صح هناك (SQLite بيرجّعه لـ OFF كل اتصال جديد)، لكن **ممنوع** تحط تحويل بيانات فيه.

# القسم هـ — التبعيات

```
Sprint 0 (بيانات)
   │
   ├──> Sprint 1 (رموز التصميم)  ← لا يعتمد على 0، لكن يجب أن يسبق 2
   │        │
   │        v
   └──> Sprint 2 (المجموعات + v3)
            │
            v
        Sprint 3 (الحلقة المباشرة)
            │
            ├──> Sprint 4 (العلامة)   ─┐
            └──> Sprint 5 (العمق)     ─┴─ متوازيان لو فيه أكتر من مطوّر
```

**المسار الحرج:** `0 → 1 → 2 → 3`. Sprint 4 و 5 مستقلان.
**لو فيه مطوّران:** Sprint 0 و Sprint 1 يتوازيان (بيانات مقابل ثيم — لا تلامس بينهما) → توفير أسبوع.

## الخلاصة

**أهم قرارين في هذه الوثيقة:**

1. **رموز التصميم تتقدّم قبل بناء المجموعات** (C2) — أسبوع واحد يوفّر أسبوعين إعادة تنسيق لـ٨ شاشات.
2. **`static const late` ما كانش هيُصرَّف** (C1) — لو اتنفّذ نظام التصميم حرفياً، البناء كان هيقف من أول يوم.

**الحالة الأخطر تنفيذياً:** migration v3 (R1) — إعادة إنشاء `Sessions` مع نقل الحضور. ده البند الوحيد اللي محتاج نسخة احتياطية إجبارية و rollback مختبَر قبل الشحن.
